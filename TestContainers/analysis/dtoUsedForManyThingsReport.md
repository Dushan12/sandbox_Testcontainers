# Data Transfer Objects Used For Many Things Analysis Report

## Overview
This report analyzes the DTOs in the codebase for nullable properties and multi-purpose usage that could allow invalid domain states.

## DTO Analysis

### Potential Invalid States

**Current Person DTO Allows:**
```scala
Person(id = "", firstName = "", lastName = "", email = "not-an-email")
```

**These are technically valid Scala values but invalid domain objects:**
- Empty strings for names
- Invalid email format
- Empty ID (should be generated)

### Recommended Improvements

**Using Refined Types:**
```scala
import eu.timepit.refined._
import eu.timepit.refined.api.Refined
import eu.timepit.refined.string._
import eu.timepit.refined.collection._

case class Person(
  id: String Refined NonEmpty,
  firstName: String Refined NonEmpty,
  lastName: String Refined NonEmpty,
  email: String Refined MatchesRegex["^[\\w.-]+@[\\w.-]+\\.\\w+$"]
)
```

**Using ADT for Status:**
```scala
sealed trait EmailStatusType
object EmailStatusType {
  case object Pending extends EmailStatusType
  case object Processing extends EmailStatusType
  case object Done extends EmailStatusType
  case object Failed extends EmailStatusType
}

case class EmailStatus(
  id: String,
  personId: String,
  requestedAt: Long,
  status: EmailStatusType  // Instead of String
)
```

## Multi-Purpose DTO Analysis

### Person DTO Purposes

| Purpose | Needed Fields | Current Fields | Match |
|---------|---------------|----------------|-------|
| Create Request | firstName, lastName, email | id, firstName, lastName, email | ⚠️ id not needed |
| Database Entity | all | all | ✅ Perfect |
| List Response | all | all | ✅ Perfect |

**Issue:** The `id` field is required on input but should be generated by the system.

**Better Design:**
```scala
// For creation (no id)
case class CreatePersonRequest(firstName: String, lastName: String, email: String)

// For storage/response (with id)
case class Person(id: String, firstName: String, lastName: String, email: String)
```

## Metric Score

**Grade: 7/10**

**Positive Findings:**
- No nullable/Optional fields in DTOs
- All fields are required, preventing partial objects
- Simple, flat data structures
- JSON codecs properly defined

**Negative Findings:**
- No validation at type level (empty strings allowed)
- `status` field is stringly-typed instead of ADT
- Same `Person` model used for both input (where id shouldn't exist) and output
- Email format not validated in type system

**Recommendations:**
1. Create separate `CreatePersonRequest` without `id` field
2. Use refined types or Newtype for validated strings
3. Convert `EmailStatus.status` to sealed trait/enum
4. Add runtime validation layer for inputs
5. Consider using ZIO Schema for automatic validation
